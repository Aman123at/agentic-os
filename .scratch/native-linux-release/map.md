# Map: Native Linux release

Charted 2026-09-17 with `/wayfinder`. Tracker: local markdown (no `docs/agents/issue-tracker.md` exists; the default convention applies).

## Destination

An **M6 section in `docs/PLAN.md`, reviewed and approved by Aman**, that specifies the native Linux (Ubuntu VPS) distribution of Agentic OS — prebuilt binaries, `install.sh`, the `aos daemon` / `aos config` / `aos model` verbs, username+password UI authentication, whole-filesystem access, and a separate documentation site — broken into sub-tasks small enough to track one by one, plus the ADRs those decisions demand.

Reached when: M6 is written, every decision below is settled, and Aman has approved it. **No implementation code is written before that approval.**

## Decisions so far

### Settled while charting (2026-09-17, three grilling rounds — no ticket)

- **Destination artifact**: an M6 section in `docs/PLAN.md` plus ADRs, not a standalone spec and not the feature itself.
- **Deployment shape**: a **native host install** becomes the primary shape — `aosd` installed to `/usr/local/bin`, run by systemd on the VPS itself, Machine == VPS. Docker Compose stays as the sandboxed alternative, and the docs state plainly that only the native install reaches the real host filesystem.
- **CLI verbs**: ~~`aos service start|stop|status|restart`~~ **reversed 2026-09-17** — `aos service <name>` was already the Services group (`internal/cli/services.go:18`). The daemon's lifecycle is **`aos daemon start|stop|restart|logs`, with `aos status` as the front door**. `aos stop --all` keeps its current meaning (stop every Agent) untouched.
- **Distribution**: prebuilt release tarballs only. No Go, Node or any toolchain required on the VPS — installing is a software install, not a build.
- **Installation is non-interactive**: no prompts, no key, no questions. Install, then configure.
- **Configuration lives in `/etc/aos/config.yml`**, root-owned `0600` — deliberately *not* under `/home/aos`, which is the Agents' writable tree. `aos config set` and the UI override at runtime; a restart re-reads the file.
- **Config precedence**: runtime changes are written back into `config.yml`, so the file stays the single source of truth and a restart never silently reverts a setting (Q19 option (b)). **Consequence, confirmed 2026-09-17:** this makes the "the file takes over on restart and resets your runtime settings" warning Aman originally asked to document *false*. The documentation says the opposite instead.
- **Port**: base **7700**, scanning upward if taken; the chosen port is written back into `config.yml` on first start (so it moves once, never again) and printed by `aos status`; an explicit `port:` pins it and fails loudly rather than moving.
- **Bind**: `0.0.0.0` (settled 2026-09-17, reversing the earlier `127.0.0.1`). A fresh install is reachable from a browser at `http://IP:7700` with no proxy in front; nginx and TLS stay optional and are the user's own business. The password screen, not the bind address, is what stands between the internet and the Machine — which raises the stakes on *The authentication model* and on the two `Host` checks, since both refuse anything that is not localhost today.
- **Authentication**: username + password, stored in the existing SQLite database, one user only. JWT access token plus a working refresh token, signup on first UI use, password change requiring the current password, logout. No email or SMS, so no forgotten-password flow. The CLI is not authenticated — it is never exposed.
- **Agent identity**: Agents run as the unprivileged `aos` user, which is in sudoers; privileged actions go through the existing Privileged Tool + Approval path, so root is reachable but always explicit and audited.
- **Agent reach**: Agents read the whole filesystem and may write outside `/home/aos`, with the existing Protected Paths asking first. Other users' homes join the built-in Protected list.
- **AOS owns its own home**: `/home/aos`, created by the installer. `PrepareHome`'s dotfile relocation must **never** run against a home AOS did not create — pointed at a live `/home/ubuntu` it would move the `authorized_keys` that is the only way into the server.
- **Replay is off in native mode**: the Install Ledger is still recorded and Checkpoint/Restore stay available but user-initiated. Re-applying the Ledger at every boot makes sense for a disposable container and is destructive on a persistent server.
- **Shared Folder is removed**, everywhere including Compose.
- **Finder's Places** become Home, Downloads, Filesystem (`/`) and Trash.
- **Mode** is a runtime setting in `config.yml`; one binary always carries the embedded Desktop (3.4 MB unpacked, so the cost is a few MB).
- **Browser is off by default**; setting `include_browser: true` and restarting fetches Chromium's headless shell at that point rather than shipping 250 MB in the tarball.
- **Upgrade/uninstall**: re-running `install.sh` upgrades in place; `aos uninstall` removes the binary and unit but keeps `/home/aos`, `/var/lib/aos` and the config unless `--purge`.
- **Docs site**: Astro Starlight, in this repo, built to static files Aman hosts on his own domain. Never served by `aosd`, never in the binary.

### Settled 2026-09-17, second round

- **Repository**: `Aman123at/agentic-os`, **private**, created and pushed this session. The five commits of M5.1/M5.2/M5.3 work plus this charting are now on `main`; the tree cross-compiles clean for `linux/amd64`.
- **One name: `agentic-os`.** It already matches the Go module's repo segment and the image name in `compose.yaml`. Consequence: the module path's *owner* segment is still wrong (`amantiwari`, not `Aman123at`) — see *Naming*.
- **Password hashing**: Go's stdlib `crypto/pbkdf2`, not `golang.org/x/crypto`/argon2id. ADR-0002 is proud of the single binary; this costs zero new dependencies.
- **YAML**: `gopkg.in/yaml.v3` is accepted as a new dependency. There is no stdlib option, and a file users hand-edit needs comments.
- **Widening Agents to `/` is approved.** The Landlock ruleset only needs to walk the *ancestor chain* of each Protected Path, not the whole filesystem, so the cost concern in *Widening the filesystem to the whole VPS* is bounded by construction — but it is verifiable only on the VPS.

- [The model catalogue: which models, and which support reasoning effort](issues/04-model-catalogue.md): the catalogue must ship as data — `GET /v1/models` reports nothing about reasoning effort — and it seeds `/var/lib/aos/models.yaml`, open rather than a strict allow-list. Found a live defect on the way: the fixed effort list in `internal/settings/settings.go:74` is missing `max`, still offers the legacy `minimal`, and is per-model in reality, where a wrong value is an HTTP 400 rather than a clamp.

- [Release engineering: multi-arch binaries and GitHub Releases](issues/09-release-engineering.md): a hand-written `release` stage in `tools/ci`, not GoReleaser, because the existing Dockerfile compiles Go itself and GoReleaser would need a second one that drifts. Version-less asset names let `install.sh` avoid the GitHub API and its per-IP rate limit entirely. Two traps found: `-ldflags -X` silently cannot write `Version` because it is a `const`, and the first tag must be `v0.1.0` — a `-m6` suffix makes GitHub treat it as a prerelease and `/releases/latest` 404s.

- [Naming: module path, repo, binary and Docker Hub namespace](issues/17-naming.md): one name, `agentic-os`, everywhere. The repo is `Aman123at/agentic-os` (private, pushed). Release assets are `agentic-os-linux-<arch>.tar.gz`, version-less so `/releases/latest/download/` resolves. Docker Hub is `aman123at/agentic-os`. Binaries stay `aos` and `aosd`; the product stays "Agentic OS". One loose end raised for Aman: the module path's owner segment still says something else. **The install URL path is settled as `/agentic-os/`** by *install.sh, written and read*, which also made `raw.githubusercontent.com` canonical with the domain redirecting to it.

- [Reach, bind and the two Host checks](issues/01-reach-bind-and-host-checks.md): both Host checks are deleted; the Origin check already handles arbitrary hosts and is the real CSRF defence, so nothing is lost. `/port/<n>/` becomes the documented forwarding form because `<port>.localhost` cannot resolve from a remote browser. **Two constraints flow out of it:** tokens must live in headers and never in cookies, or DNS rebinding comes back; and the first-run window is closed by initial credentials in `config.yml` plus a mandatory password change on first login, with the pre-reset token restricted to that one call.

- [The authentication model: JWT, refresh, and the WebSockets](issues/02-authentication-model.md): one **single-use 30-second ticket** authenticates every browser-initiated load — both WebSockets, `<img>`/`<video>` on `/files/raw`, the PDF ranges and the download anchor — because removing cookies removes what served all four. Refresh in `localStorage` (XSS-readable, stated plainly), access in memory, 15 min / 30 days, rotated on use with family revocation on replay. `users` and `refresh_tokens` in `0005_m6.sql`; signing key in `/var/lib/aos/`, not in `config.yml`. `AOS_ACCESS_TOKEN` and `aos desktop-url` are deleted outright. Found on the way: **`http://IP:7700` is not a secure context**, so Service Workers, `crypto.subtle` and the async clipboard API are all unavailable.

- [Widening the filesystem to the whole VPS](issues/06-widening-the-filesystem.md): Agents **already** read all of `/` — `Plan` carves Read+List from `/` today — so only `Writable` changes, to `/` minus an explicit Protected list (`/boot`, `/proc`, `/sys`, `/snap`, `/root`, other homes, the AOS binaries and unit), with `/var/lib/aos` and `/etc/aos` Hidden and `/dev` still Writable. The walk cost is bounded because `carve` only descends into directories containing an exclusion — **which makes "no exclusion may live under `/proc` or `/sys`" a hard rule**. The real hazard is `Ruleset.Stale`: `/etc` becomes a split directory, so every package install re-plans, and `/run` churns on a real server in a way it never did in a container. Trash generalises to `.Trash-<uid>` at the mount root — the Shared Folder's existing code, moved rather than deleted.

- [/etc/aos/config.yml: schema, validation and the `aos config` verbs](issues/05-config-file.md): the file replaces the **SQLite settings table**, which was the real source of truth until now (`internal/settings/settings.go:1`), so there is one store and one precedence chain. Write-back uses `yaml.v3`'s `Node` API, which round-trips comments and key order, written atomically via temp file plus `rename()`. A malformed file or an **unknown key** refuses the start rather than falling back to defaults. Startup-only keys are accepted, written and marked *(pending restart)*. Compose gets the same file, generated from the environment on first start, so there is only ever one configuration system. **The restart warning Aman asked for by name is dropped** — write-back makes it false, and the documentation now says the opposite.

- [The systemd unit and the `aos service` lifecycle](issues/10-systemd-and-service-lifecycle.md): `/etc/systemd/system/aos.service`, `Type=notify` so `install.sh` cannot race the listener, `Restart=always` with a start limit so a malformed config fails instead of looping, `KillMode=mixed` and `TimeoutStopSec=60s`. **The hardening directives are absent on purpose**, argued by layer in a comment inside the unit itself: systemd confines `aosd` and every descendant indiscriminately, where Landlock plus uid separation confines each Agent process precisely. Three things the code forced: **`aos service` was already the Services group**, so the daemon's verb becomes `aos daemon` with `aos status` as the front door; **the control socket is `0666` and unauthenticated**, which is harmless in a one-user container and a local root API on a VPS, so it becomes `0600` root-only with a uid check; and **the 20-second HTTP shutdown runs before Tasks are drained**, so Compose's 30-second grace can already SIGKILL mid-drain. Also noted: an unattended restart **denies every pending Approval** (`internal/task/manager.go:140`).

- [install.sh, written and read](issues/11-install-script.md): prototyped in [`tools/spikes/install/`](../../tools/spikes/install/), rehearsable with `DRY_RUN=1` from any machine. POSIX `sh`, `set -eu`, body in a `main()` called on the last line so a truncated `curl | sh` does nothing. Version-less assets mean no GitHub API call; `grep`-then-`sha256sum -c` because `--ignore-missing` passes vacuously; `install` + `mv` because writing over a running binary is `ETXTBSY`. **The installer installs nothing but `aosd`** — the image's `machine` stage (25 apt packages, a curated Node, a global apt-cache redirect, `userdel -r ubuntu`) is free in a disposable image and unacceptable on someone's server. No rollback: every step is idempotent, so **re-running is the repair**. An upgrade refuses while a Task is running. Two container assumptions caught: **`useradd --uid 1000` is the administrator's uid** on stock Ubuntu, and the `NOPASSWD:ALL` sudoers grant means the Desktop password is root on a real VPS — kept, but now said out loud.

- [Which decisions become ADRs](issues/15-which-decisions-become-adrs.md): **two new, five amended, written in the same commit as M6.** New: **ADR-0009** *The Machine is the host: a native Linux install* (the umbrella the container-era ADRs point at, carrying the absent hardening directives and the sudoers reality) and **ADR-0010** *Configuration lives in one file, and runtime writes back to it*. Amended in place: **0007** (thesis survives and strengthens under a public bind, so the number and title keep but the opening paragraph is rewritten, not appended to), **0004** (a dated widening section — the ruleset is the spec the sandbox code cites, so it is never forked), **0003**, **0005**, and **0008** (owed to ticket 12). Rule stated: *new ADR when the thesis changes, amendment when only the mechanism moves, and an ADR code cites as a spec is edited in place.* Found on the way: **ADR-0008 justifies `--no-sandbox` by "the container is the outer boundary"** — natively both the reason and the boundary vanish at once, leaving an unsandboxed browser as a sudoers uid. Also falsified: 0004's "Docker secret file" key custody and its env-var spellings, and 0003's opening premise.

- [Removing the Shared Folder](issues/07-removing-the-shared-folder.md): **deleted as a concept and replaced by nothing.** `Ops.Shared` and `Layout.Shared` go; Trash selection becomes an **`st_dev` comparison**, not a path prefix — same device as home → the home Trash, otherwise `.Trash-<uid>` at the mount root found by walking up until the device changes. On a one-filesystem VPS that means deleting `/etc/nginx.conf` is a plain rename into `~/.local/share/Trash`, nothing is created at `/`, and the "unwritable mount root" refusal almost never fires — under a prefix rule it would have fired on **every** delete outside home, since uid `aos` cannot create `/.Trash-1000`. The item ID stops being a `home`/`shared` enum and becomes a structurally validated absolute path. **`PrepareHome` must actively remove the `~/Shared` symlink**: it is root-owned in a sticky `1775` home, so deleting only the creating code strands a link no user or Agent can ever delete. Compose gets nothing named — a plain bind mount into home, no Protected entry, no symlink — **which also deletes the repo's most-documented setup failure**, since `/shared` is the only bind mount in `compose.yaml` and the reason Docker Desktop hangs on `~/Desktop`. Ordering settled: this lands **before** the filesystem widening.

- [The authentication screens and account lifecycle](issues/03-authentication-ux.md): the login screen is the **`needs-signin` boot phase promoted** (`App.tsx:22` already has it), the forced first change is a third boot phase, and an expired session is a **modal over the desktop, never a bounce** — `sessionStorage` restores the window layout on reload, but unsaved TextEdit buffers and terminal scrollback die with it. Refresh runs **proactively on a timer**, because a 401-triggered refresh queues behind the held streams that already occupy the browser's six HTTP/1.1 connections. Logout revokes the refresh family server-side **and closes the streams and WebSockets that family authorised** — nothing re-checks a held connection, so without that "sign out" is decoration. Twelve characters minimum, refused not warned; changing the password signs every other session out; `sudo aos user passwd` is the only recovery there is, and `username` in `config.yml` stays authoritative so renaming is a config edit. Two things nobody had booked: the **`cli` → `ui` switch is the account-creation moment** (a circular handoff between tickets 01 and 08 that neither owned), and **the forwarder is composed outside the authenticator** (`daemon_linux.go:198`), so deleting the Host guard on a public bind would have put every Agent-started port on the internet unauthenticated. Forwarded Services move inside the session: the existing single-use ticket, exchanged for a cookie scoped to `Path=/port/<n>/`.

- [Mode switching and the single binary](issues/08-mode-switching.md): **`cli` Mode starts no TCP listener at all** — it listens on the Unix socket and nothing else. That was found, not assumed: `daemon_linux.go:198,229` starts the listener unconditionally today, so ticket 01's "in `cli` Mode nothing is exposed" was aspirational, and on a public bind it would have published every Agent-started port through the unauthenticated forwarder in the one Mode that has no account. The `desktop` build tag and `embed_none.go` go; `Assets()` returns nil when `dist/index.html` is absent, because the test stage never builds the Desktop and cannot carry a build-time requirement. The Dockerfile's two targets collapse into one image — **they measured 1 MB apart** (m0 F3), so the split only ever bought build time — taking `AOS_IMAGE_MODE` and the `main.go:45` refusal with them. The verb is **`aos mode ui`**, which guards, generates and prints the password, writes and restarts; but the invariants live in `aosd`'s start path, because the config file is hand-editable and `systemctl` needs no CLI of ours. The guard blocks on running and awaiting-user Tasks and **never on queued ones** — `recover` re-queues those untouched — and `--force` interrupts rather than cancels, printing the `aos resume` lines, because that is what an unattended restart already does. `ui` stays the default. Found on the way: the Agent prompt carries **three** false sentences natively, and the unbooked one — "The Machine restarts with a fresh system" — is the behaviour-shaping one.

- [Installing Chromium lazily, and Compose parity](issues/12-lazy-browser-install.md): **Playwright leaves the runtime entirely** — checked, not assumed: `cdn.playwright.dev/builds/cft/<chrome-version>/…` 307s to Google's `chrome-for-testing-public` bucket, and the key is the **Chrome version string**, not Playwright's revision. So the fetch is one GET of a 120 MB zip, pinned by a Chrome version plus **a sha256 we pin ourselves**, because Playwright verifies nothing at all. `sudo aos browser install` does it — explicitly, never during a start — checks `DT_NEEDED` against `ldconfig -p` with stdlib `debug/elf` rather than running a just-downloaded binary under `ldd`, refuses under 1 GB free, and writes `include_browser: true` itself. It stays **out of the Install Ledger**: Restore would otherwise `apt-get remove` the browser's libraries out from under a browser the config still says is on. **The published image carries no Chromium and no browser libraries either** — true parity, one code path, and it leaves the Dockerfile with exactly one runtime stage. Two findings on the sandbox: the setuid `chrome_sandbox` path is dead twice over (it is not in the headless-shell zip, and `no_new_privs` would make it inert), and ADR-0008's replacement boundary had been quietly lost — **the browser borrows the *Agent* ruleset**, so M6's widening to `/` would have handed an unsandboxed Chromium write access to the whole server. It gets its own allow-list ruleset instead, landing before or with the widening.

- [The documentation site](issues/13-documentation-site.md): prototyped at [`tools/spikes/docs-site/`](../../tools/spikes/docs-site/) — Astro 7 + Starlight 0.42, fifteen pages, `base: "/agentic-os/"` because a sub-path deploy with the default base 404s **only on the real host**. The command reference is **generated** from the cobra tree by 120 lines of our own rather than `cobra/doc`, whose package would pull `go-md2man` and `blackfriday` into a module graph ADR-0002 is proud of; drift is caught in `lint` like `gofmt -l`, and the Astro build is an optional `docs` stage. But the finding that matters is not about documentation at all: **the repository is private, and every URL the project has settled on 404s because of it** — `raw.githubusercontent.com/…/install.sh` and `/releases/latest/download/…` were both measured at 404, GitHub Pages is unavailable on a private repo under Free, and ticket 17 had recorded *private* as a fact that nobody carried forward. **The repository goes public at the first tag**, as an M6 sub-task ordered ahead of the release stage. Two more: Starlight has no built-in versioning (it is a third-party plugin, so the answer is one version, deployed on tag), and **`README.md` needs rewriting whole** — tickets 07 and 12 book two line-edits to a file whose thesis is Docker and whose Troubleshooting section is entirely about the Shared Folder.

## Not yet specified

- **What software a native Machine has.** The Docker image curates ~25 apt packages plus a pinned Node; `install.sh` installs none of them, and `internal/agent/instructions.go` promises Agents `pipx` and `npm` on a box that may have neither. Agents can install what they need through the Install Ledger, but whether a first Task should have to is a product question nobody has asked. A sub-task of M6 in its own right.

- **Which Ubuntu the VPS runs.** It decides whether Chromium's own sandbox *could* work at all: 22.04 allows unprivileged user namespaces, 24.04+ refuses them by AppArmor. M6 keeps `--no-sandbox` either way, because the product must run on both — but the ADR states the dependence rather than claiming a flat impossibility, and the answer is a question for Aman, not for this Mac.

- **Data migration for existing Compose users.** Someone running the Compose image today has a home volume, a SQLite database and an Install Ledger. Whether the native install can adopt that state, and how, is unclear until the native layout is fixed.
- **Non-Ubuntu Linux.** Aman said "Ubuntu or any linux distribution". Debian is free; RHEL-family is untested. **The non-systemd half is settled**: `install.sh` checks `/run/systemd/system` and refuses cleanly, with Compose named as the alternative and no PID-file fallback. How far `install.sh` stretches across distributions is still open.
- **What `aos doctor` means without a container.** *(One piece settled: the `(image built for …)` parenthetical at `internal/cli/doctor.go:31,35` dies with `AOS_IMAGE_MODE`, and in `cli` Mode the Mode line says there is no HTTP listener.)* Half its checks (`--host-check`, forwarding, the secret mount) describe a Host/Machine boundary that no longer exists natively. The replacement check-list depends on the sandbox and systemd decisions, **both of which are now settled, so this is unblocked**.
- **Performance targets (§16) on a VPS.** The existing targets assume Docker Desktop on Apple Silicon. A 1-vCPU VPS will miss several. Which targets apply natively, and what they become, can't be set until the install exists to measure.
- **Finder against pseudo-filesystems and huge directories.** `/proc`, `/sys` and `/usr/lib` will be reachable for the first time. The shape of the fix (exclusions, lazy counting, a depth guard) depends on how the filesystem widening lands.
- **Whether `/etc` Checkpoints still earn their place** once Replay is off and the box is persistent.
- **The cost of a re-plan on a real VPS.** Bounded by construction, but the number — and how often `/run` churning triggers it — can only be measured on Ubuntu. The one open question this ticket could not close from a Mac.
- **Whether the milestone-derived version scheme survives.** `version_linux_test.go` ties `Version` to the newest `### M<n>` heading in the plan, which fights tag-derived release versions. Reconciling them is now unblocked — naming and release engineering are both settled.
- **When the module path gets renamed.** `github.com/amantiwari/agentic-os` should be `github.com/Aman123at/agentic-os`. Mechanical but tree-wide, and it wants its own commit before the first tag, not folded into M6's work.
- **What a scanner finds on port 7700 before nginx.** The sign-in page is public by default now. Whether it should carry any fingerprinting resistance — a generic title, no version string — is unasked.
- **Whether a signed-in user should be able to publish a Service deliberately.** M6 keeps today's rule — any Service is reachable to the signed-in user, now through a ticket — but a per-Service "publish" with its own long-lived link is the obvious next ask from anyone running something they want a colleague to see. Deliberately not designed.

- **What else assumed a secure context.** Service Workers, `crypto.subtle` and the async clipboard API are gone on a plain-http VPS. Auth no longer needs them, but nothing has swept the rest of the Desktop for the assumption.
- **SQLite growth on a box that runs for months.** `task_steps` and the audit log have no retention. Service logs rotate and the journal is journald's business, so this is the one unbounded store left. Retention is its own decision. *(All that remains of the observability entry, which `The systemd unit` otherwise closed.)*

## Out of scope

Ruled beyond this destination. These do not graduate; they would need a new effort.

- **macOS and Windows native installs.** Aman: "do not care about other OS."
- **Email or SMS password recovery.** Explicitly excluded — no mail or OTP service, so no forgotten-password flow at all.
- **Multiple users, roles or permissions.** One user, one password.
- **TLS terminated by `aosd` itself.** The user puts nginx in front; certificates are their business.
- **Model providers other than OpenAI.** Unchanged from the v1 plan's non-goals.
